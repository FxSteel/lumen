============================================================
1) RESUMEN EJECUTIVO
============================================================
Nova es una aplicacion web para operacion de contenido en vivo en contexto de iglesia/eventos.
El producto ya cubre el flujo central: login, workspace activo, gestion de canciones/slides,
integracion biblica (YouVersion) y salida en vivo para pantallas principal y escenario.

Madurez general actual: MVP avanzado / pre-produccion.

Estado sintetico:
- Valor de negocio: alto y claro.
- Flujo principal: funcional de punta a punta.
- Riesgo tecnico principal: seguridad y gobernanza de APIs con service role.
- Riesgo operativo principal: bajo nivel de testing automatizado.
- Riesgo de mantenibilidad: medio-alto por deuda de estructura y logging excesivo.

Recomendacion ejecutiva:
- Si van a escalar usuarios/workspaces, priorizar hardening de auth/API en 2-3 semanas.
- En paralelo, cerrar base de calidad (tests + observabilidad + runbooks).
- Luego, pasar a roadmap de crecimiento (usuarios, integraciones, AI builder, multi-workspace).

============================================================

============================================================
3) PROPOSITO FUNCIONAL DEL PRODUCTO
============================================================
La aplicacion permite a un operador controlar contenido proyectado en tiempo real:

A. Operacion de canciones
- Crear canciones por workspace.
- Editar metadata (autor, tonalidad, bpm).
- Gestionar slides por cancion (tipo, contenido, posicion, font_size).

B. Contenido biblico
- Elegir version biblica (es/en) desde YouVersion.
- Navegar libro/capitulo/versiculos.
- Enviar versiculo seleccionado a salida en vivo.

C. Broadcast en vivo
- Pantalla principal (audiencia): slide, logo, anuncio, clear.
- Pantalla escenario (musicos): contenido + hora + mensaje de escenario.
- Sincronizacion entre ventanas por BroadcastChannel (baja latencia, mismo navegador/origen).

D. Multi-tenant por workspace
- Cada usuario opera en su workspace activo.
- Configuracion por workspace: logo, anuncio, idioma y ajustes de stage.

============================================================
6) HALLAZGOS CRITICOS (PRIORIDAD P0)
============================================================
P0-1: Validacion de token insuficiente en endpoints sensibles
Rutas observadas:
- app/api/bootstrap/route.ts
- app/api/auth/workspaces/route.ts

Situacion:
- Se usa jwt-decode para extraer claims del token sin verificar firma/expiracion.

Riesgo:
- Riesgo de suplantacion/logica de autorizacion incorrecta si se acepta payload no validado.

Recomendacion:
- Siempre validar token con Supabase Auth getUser(token) o verificacion JWT criptografica.
- Prohibir decisiones de autorizacion basadas solo en decode local.

P0-2: Uso amplio de SERVICE ROLE sin una capa de policy estricta
Situacion:
- Varias rutas usan service role para operaciones de DB.

Riesgo:
- Error en validacion o filtro puede impactar aislamiento de tenants.

Recomendacion:
- Introducir capa server de autorizacion por actor/workspace.
- Minimizar endpoints con service role y encapsular consultas criticas.
- Agregar auditoria de acceso por workspace_id y user_id.

============================================================
7) HALLAZGOS ALTOS (PRIORIDAD P1)
============================================================
P1-1: Logging excesivo con datos operativos
- Hay gran cantidad de console.log en frontend y backend, incluso con payloads y metadatos.
Riesgo: ruido, fuga de informacion operativa, costo de debugging en produccion.
Accion: politicas de log level + sanitizacion + remover logs de contenido en vivo.

P1-2: Cobertura de pruebas automatizadas casi nula
- Solo hay scripts manuales puntuales (ejemplo YouVersion), sin suite de regresion estable.
Riesgo: cambios rompen flujos clave sin deteccion temprana.
Accion: baseline de tests: auth/workspace API + operador critical path + smoke E2E.

P1-3: Deuda de estructura y duplicacion de patrones Supabase
- Convivencia de clientes/supabase wrappers y rutas de auth/workspace parcialmente redundantes.
Riesgo: mantenimiento lento, errores de consistencia.
Accion: consolidar cliente server/browser y estandar de acceso a datos.

============================================================
8) HALLAZGOS MEDIOS (P2)
============================================================
P2-1: README principal no describe el producto
- Sigue plantilla default de Next.js.
Impacto: onboarding tecnico lento.

P2-2: Navegacion con modulos visibles pero deshabilitados
- Usuarios, Integraciones, AI builder aparecen pero no activos.
Impacto: expectativa funcional confusa.

P2-3: Mucha documentacion historica en raiz
- Hay decenas de archivos .md de entregas/fixes.
Impacto: dificultad para distinguir documentacion vigente vs historica.

P2-4: BroadcastChannel limita sincronizacion a mismo origen/navegador
Impacto: correcto para setup local, pero no cubre operacion distribuida multi-dispositivo.

============================================================
Fase 0-30 dias (Hardening y control)
1. Corregir validacion de tokens en todas las rutas server.
2. Revisar y reducir uso de service role.
